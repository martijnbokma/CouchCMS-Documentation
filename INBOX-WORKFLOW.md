# Inbox → published MDX workflow

Standard pipeline for turning **raw drafts** in `.inbox/` into **Starlight-compatible** pages under `src/content/docs/`. This aligns with [Starlight authoring guidance](https://starlight.astro.build/guides/authoring-content/) (YAML frontmatter, MDX where components are needed) and with **CouchCMS documentation policy**: preserve the original author’s intent and wording—especially for material by **Kamran Kashif**—and change only what is **strictly required** for a valid, accessible, English site.

## Principles (non-negotiable)

1. **Minimal edit** — Treat inbox files as **source manuscripts**. Do not rewrite for “clarity,” shorten tutorials, or modernize tone unless a ticket explicitly requests it.
2. **Preserve code** — Follow `.cursor/rules/markdown.mdc`: **do not alter code blocks** except when fixing an objective error (broken tag, wrong attribute) or splitting for MDX syntax. Never “improve” Couch examples.
3. **Preserve voice** — Keep explanations, section order, and emphasis unless a technical requirement forces a change (e.g. heading hierarchy for accessibility).
4. **English only** — Published pages must be English. If the inbox draft is another language, **translate faithfully** without adding interpretation.
5. **Mechanical conversion** — Most work is **formatting**: frontmatter, headings, links, images, components—not redrafting.

## What counts as “strictly necessary” changes

Allowed without extra approval:

- Adding valid **YAML frontmatter** (`title`, `description`, `keywords`, `category`, `author`, `lastUpdated`, `sidebar.order` as required by [STYLEGUIDE.md](./STYLEGUIDE.md)).
- Fixing **structural** Markdown/MDX issues: heading levels (no skipped `##` → `####`), list indentation, fence languages, **internal links** with **trailing slashes**.
- Replacing forum/HTML junk with valid MDX: bare `![...]` in `.mdx` → Astro `<Image />` + imports; moving assets under `src/assets/img/` with descriptive names.
- **Obvious** typos that break rendering or mislead (e.g. broken fence, `</cms:editable>` typo). Prefer a **single** reviewer note in the PR if unsure.
- Converting deprecated paths or forum URLs to current **internal doc links** where the mapping is unambiguous.

**Not** allowed as “necessary” by default:

- Rewriting paragraphs, merging sections, or “SEO tuning” copy.
- Changing Couch tag names, parameter names, or example values to match personal preference.
- Adding new examples or deleting edge cases the author documented.

If a change is editorial (not mechanical), **label it in the PR** and get a **human** sign-off.

## Standard workflow (repeat for every inbox file)

### 1. Intake

- [ ] Note **source** (forum post URL, email, file name) and **CouchCMS version** if stated in the draft.
- [ ] Confirm **target section**: concepts vs tags (see [AGENTS.md](./AGENTS.md) and repository conventions). Long, multi-tag guides usually belong under **`concepts/`**; single-tag reference under **`tags-reference/`**.
- [ ] Choose **`sidebar.order`** after the nearest sibling page (Starlight orders pages within autogenerated groups).

### 2. Prepare the working copy

- [ ] Work on a **branch**; keep the original inbox file until the PR merges (or archive a copy in git history only).
- [ ] Run `pnpm run validate` on the repo before large edits to establish a baseline.

### 3. Conversion (use the project prompt)

Use the converter prompt so rules stay consistent:

```text
@.cursor/prompts/convert-to-markdown.md

Convert the following inbox draft to MDX for [target path under src/content/docs/...].
Preserve all code blocks and Kamran’s wording; only apply STYLEGUIDE mechanics.
```

Paste the **full** inbox content after that block.

### 4. Mechanical checklist (before PR)

- [ ] **Frontmatter** complete and valid; `description` quoted if needed per YAML rules.
- [ ] **First heading** after frontmatter follows hierarchy (often start at `##` for Starlight page title behavior—match existing pages in the same folder).
- [ ] **Code blocks**: language + `title="..."` where the style guide expects a title; **diff blocks** left untouched byte-for-byte.
- [ ] **Tag links**: [**editable**](../../tags-reference/core/editable/) style (bold, lowercase tag name).
- [ ] **Images**: `import { Image } from "astro:assets";` + import paths; **alt** text; caption in `>` blockquote per [README.md](./README.md).
- [ ] **Admonitions**: Starlight `:::note` / `:::tip` / etc., not raw HTML unless already required.
- [ ] **Document end**: horizontal rule `---` and optional “Next” link if the section uses that pattern.

### 5. Verification

```bash
pnpm run validate
pnpm run lint:md    # if touched paths are included
pnpm run build      # must succeed; Starlight reports broken internal links
```

### 6. Pull request

- [ ] Title: `docs: add [topic] from inbox` (or `docs: promote [file] to concepts/...`).
- [ ] PR body: link to **source**; list **mechanical-only** edits vs **content** edits (should be none or called out).
- [ ] Request review from someone who can judge **fidelity** to the original.

## File locations

| Location | Role |
| :--- | :--- |
| `.inbox/` | **Drop zone** for unconverted drafts (forum exports, notes). Not published. |
| `src/content/docs/.../*.mdx` | **Published** documentation. |

Optional: add a one-line `README.md` inside `.inbox/` pointing to this file so contributors know the rules.
